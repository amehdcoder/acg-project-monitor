# Architecture rules

- Keep major longitudinal tabs separate from grouped navigation and project-gated — why: direct reporting without duplicate entries or permission bypass.
- Workspace groups with a hub open their permission-filtered card page directly rather than a dropdown — why: one entry point without duplicate navigation.
- Dispatch CCFF paths to a standalone form-only shell before mounting workspace providers; use anonymous public-function requests and published QR origins — why: community visitors cannot enter records through form navigation, shared overlays, error states or editor-only links.
- Filter tours by visible destinations, effective permissions and configured components — why: guidance matches access.
- Hand Cards: protected standalone route rendering the same live record-backed document as exports; exports capture the naturally flowing front/back layouts with independent page aspect ratios; camera start/stop serialized with stale sessions cancelled, torch only when the running track supports it — why: consistent viewing/downloads, no public beneficiary data, no cropping or leaked cameras.
- Facility branding: logos upload to the private `facility-logos` bucket (`<project>/<facility>.<ext>`), path stored in `health_facilities.logo_url`, resolved via signed URL; the hand card swaps the default partner logo/name for the beneficiary's facility when set — why: per-facility cards without exposing media publicly.
- Non-admin focal assignments override team navigation; wait for facility access, reuse facilityScope for clinical views, enforce restrictive RLS alongside grants, and require all registered household members to be in scope before revealing a whole household — why: project grants and mixed-facility households must not bypass privacy.
- Protected records read-cache keys include the authenticated user; cache updates retain that namespace — why: shared devices must never show another account's cached records.
- DHIS2 indicator labels follow the national standard "Number of …" wording in `nationalIndicators.ts` (mirrored in `_shared/`); mappings key off stable `key`, never the label — why: renames never break existing DHIS2 mappings.
- Route all DHIS2 reporting/dashboard imports through `health-exchange`; maps use bundled Nigeria LGA/State/National boundaries — why: secrets server-side, exact geography.
- Revoke browser EXECUTE on SECURITY DEFINER trigger/internal functions; keep it only for RLS helpers and app-called RPCs — why: smaller attack surface.
- Self-hosting: Dockerfile + nginx.conf, backend on Lovable Cloud — why: no badge.
- Records/report: reads via `offlineReadCache.cachedRead`; writes via `offlineWrite.offlineMutate` (client ids, queued ops); single-tab, backoff, jittered flush — why: full offline use, no stampedes.
- Street View uses the shared Google panorama viewer with official imagery and street-level fallback — why: consistent quality.
- Data Cleaner / record quality brain: no hand-written rules; flags come from the on-device autoencoder + transformer worker (dataCleanerBrain.worker.ts, IndexedDB memory) and, past 5,000 steps, the `brain-train` edge function every 30 min (pg_cron, lease via `claim_brain_for_training`); checkpoint in `brain_models` (most-trained wins), flags in `brain_flags`; `_shared/brain/*` mirrors `src/lib/dataCleaner/neural/*` — why: "normal" is learned cumulatively, even with nobody online, within edge CPU limits.
- Microplanning DHIS2 push/pull runs as `mp_*` actions in `health-exchange`, KPI matching in `_shared/microplanExchange.ts`, mappings as `mp:<kpi>` rows, pulled rows upserted by `microplan_entries.external_ref` — why: one server-side exchange path, idempotent re-pulls.
- Geo Microplanning workspace locks live in `microplan_workspace_locks` (user_id NULL = whole project); Owner/Co-owner/Super Admin manage and are never locked — why: mirrors the records-only shell without a side menu.
- Health-worker/programme-staff record scope is enforced in RLS via `user_programme_areas`/`beneficiary_in_user_scope`/`service_in_user_scope` (area regexes mirror `projectTeam.ts` AREA_PATTERNS); each Cases DHIS2 server may set `programme_area` so pushes contain only that area's totals — why: UI filters alone don't protect data; multi-server pushes must not duplicate programmes.
- Typed (custom) component services live per project in `project_custom_services` and typed final outcomes in `project_custom_outcomes` (keyed by component + lifecycle action, realtime), device storage only as offline fallback published on next load — why: every project user sees the same service and outcome lists.
- Livelihood uses cached record/WG/clinical evidence, person/offer assessments and offline decisions; manual provenance in `profile.graduation` survives rescoring; shared service matching drives Overview — why: consistent recommendations, human decisions and delivery tracking.
- Beneficiary care journeys derive from live services, referrals, cached linked case searches and Graduation gates, using only permission-visible components beside Overall Progress — why: consistent evidence-based progress without exposing unrelated programme participation.
- Follow-up reminders: WhatsApp in `send-whatsapp-reminders` (pg_cron 07:00 UTC, Meta credentials in server-only `whatsapp_settings`, dedup in `followup_reminders` by beneficiary + `next_follow_up_date`, outcomes in `whatsapp_notification_log`); SMS in `send-sms-reminders` (07:05 UTC, SMS Gateway for Android Basic auth, server-only `sms_settings`, `sms_*_sent` dedup, `sms_notification_log`) — why: tokens never reach the browser; each stage sends once per channel.
- Logframes: project JSON, staged editor, unique codes, Excel round-trip; referral completion = completed/all × 100, not cumulative — why: consistent reporting.
- External integrations: project-scoped hashed `amk_` keys and HMAC webhooks, wake-on-enqueue + hourly retry; validate cursors and public HTTPS destinations, reject redirects — why: signed data, no browser credentials or internal destinations.
- Donors: own Auth accounts, standalone login/signup/recovery; dashboard API uses donor RPCs/RLS + protected donor_viewers associations, never project assignments; local selection is not authorization; server risk totals — why: private aggregate-only dashboards. Report events follow entries; retries retain payloads.

- Assessments reuse QuizBuilder/server scoring; keys append to unpublished quizzes; pair by quiz/source/person. Exact activity links feed reporting-only aggregates by post-test month; dedup activity/person; user-scoped caches — why: no wrong-training totals.
- The app's landing tab is the records workspace and that workspace's landing view is its Overview hub; people without records access keep Forms as home — why: one homepage that opens on project results without dead ends.

- Access studio: per-project category access in `project_access_profiles` (Super Admin write); members follow a category via `permissions.access_category`, `hidden_views`/`hidden_sections` hide pages and profile tabs; "View as" uses the same profiles and never changes real access — why: one source of truth for what each kind of user sees.
